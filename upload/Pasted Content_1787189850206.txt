============================================================
MASTER IMPLEMENTATION PLAN
CLOUD-NATIVE VIDEO SHARING PLATFORM
============================================================

You are implementing a production-quality, cloud-native web application
that acts as a video-sharing platform conceptually similar to TikTok.

This is an academic/project implementation, but it must be designed using
real production-oriented architecture rather than a frontend-only mockup.

The application must use Microsoft Azure as the primary cloud platform.

============================================================
CRITICAL DEVELOPMENT RULES
============================================================

1. DO NOT immediately start writing the UI.

2. DO NOT create a mock frontend that pretends the backend exists.

3. DO NOT store video files inside the relational database.

4. DO NOT put Azure credentials, storage account keys, database passwords,
   client secrets, or other secrets inside frontend code.

5. DO NOT allow consumers to upload videos.

6. DO NOT rely only on frontend UI restrictions for authorization.
   All permissions must also be enforced server-side.

7. DO NOT expose Azure Blob Storage credentials to the browser.

8. Use secure, short-lived upload authorization for direct browser-to-Blob
   uploads.

9. Use exact and consistent terminology throughout the entire application.

10. Do not invent functionality that has not been requested.

11. Do not replace the requested cloud architecture with local storage,
    mock APIs, JSON files, or in-memory data.

12. Do not skip database design, API design, authentication,
    authorization, security, validation, error handling, testing,
    deployment, or documentation.

13. Before implementing each phase, verify that the previous phase is
    complete and working.

14. Never silently change the architecture.

15. If a technical decision is necessary, choose the simplest production-
    appropriate solution that satisfies the requirements and document it.

PHASE 2 — TECHNOLOGY DECISION
============================================================

Use an architecture compatible with Microsoft Azure.

Frontend:

- Static web application.
- HTML/CSS/JavaScript or another framework that can produce a static build.
- Responsive design.
- Mobile-friendly consumer experience.
- Desktop/tablet-friendly admin and creator interfaces.

Backend:

- REST API.
- Azure-hosted.
- Stateless application architecture where practical.
- Clear separation between routes/controllers, business logic,
  data access, authentication, and storage services.

Database:

- Azure Database for PostgreSQL.

Media:

- Azure Blob Storage.

Authentication:

- Microsoft Entra-based authentication where appropriate.

Secrets:

- Azure Key Vault and/or secure environment configuration.

Monitoring:

- Azure Application Insights / Azure Monitor where available.

IMPORTANT:

Do not use Azure Media Services.

For media processing, if required, use a currently supported Azure-compatible
approach such as application/container/serverless processing with FFmpeg
or another supported service.

Do not implement deprecated Azure Media Services architecture.

PHASE 6 — AUTHORIZATION
============================================================

Authorization must be enforced on the backend.

Permission matrix:

                 ADMIN   CREATOR   CONSUMER

View videos        YES      YES       YES
Search videos      YES      YES       YES
Play videos        YES      YES       YES
Comment            YES*     NO        YES
Rate               YES*     NO        YES
Upload video       YES*     YES       NO
Edit own video     YES      YES       NO
Delete own video   YES      YES       NO
Create creator     YES      NO        NO
Manage creators    YES      NO        NO
Manage users       YES      NO        NO
Moderate content   YES      NO        NO

* If implemented as administrative/moderation capability.

Every protected API endpoint must independently verify:

1. Authentication
2. User identity
3. User role
4. Resource ownership where applicable
5. Permission

Never trust role information supplied directly by the browser.

PHASE 7 — STORAGE ARCHITECTURE
============================================================

Use Azure Blob Storage for video media.

Do NOT store video binaries inside PostgreSQL.

Suggested logical structure:

videos/
    {video-id}/
        original/
        processed/
        thumbnails/

The exact structure may differ if there is a better implementation.

The database should store references/identifiers to the media.

Do not expose storage account keys to the frontend.

PHASE 8 — SECURE VIDEO UPLOAD
============================================================

Implement direct browser-to-Blob upload.

The preferred flow is:

Creator
   |
   | Select video
   v
Frontend
   |
   | Request upload authorization
   v
REST API
   |
   | Validate creator permission
   | Validate file metadata
   | Generate short-lived upload authorization
   v
Frontend
   |
   | Direct upload
   v
Azure Blob Storage
   |
   | Upload complete
   v
Frontend
   |
   | Notify API
   v
REST API
   |
   v
PostgreSQL metadata

Use short-lived, narrowly scoped authorization for upload.

Prefer Microsoft Entra-backed/user-delegation mechanisms where appropriate.

The browser must never receive:

- Storage account key
- Database credentials
- Application secrets

Validate:

- File type
- File size
- Filename
- Extension
- MIME type
- Creator authorization

Do not blindly trust the file extension.
